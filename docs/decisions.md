# 決策紀錄

記錄「為什麼這樣做」，以及**決定不做、延後、或被否決的方案**——後者最容易在對話中流失，
三個月後回來又得重新推導一次。

「改了什麼」的時間軸請見 [`CHANGELOG.md`](../CHANGELOG.md)。
實作規格請見 [`.spec/specs/`](../.spec/specs/)。

格式：每則記錄 **背景 → 決定 → 理由 → 否決的方案 → 重新評估的條件**。

## 1. 蝦皮瀏覽器爬蟲不在 CI 上執行

**日期**：2026-08-27　**狀態**：已確認（實測）

**背景**：每日雲端排程的蝦皮資料長期為 0 筆。

**決定**：蝦皮瀏覽器爬蟲只在住宅／行動網路執行，CI 只跑 PTT 與 Carousell。

**理由**：原先列出四個原因，實測後區分為：

| 原因 | 可否在 CI 解決 |
|---|---|
| session 未帶到 runner | ✅ 可（存成 secret） |
| headless 撞登入牆回傳空 list | ✅ 可 |
| camoufox 瀏覽器核心未安裝 | ✅ 可（`camoufox fetch`） |
| **蝦皮判定 runner IP 為爬蟲** | ❌ **不可** |

補齊前三項後實測，runner 帶著 22 個有效 cookie 仍被導向
`shopee.tw/verify/captcha?...&scene=crawler_item`。`scene=crawler_item` 是蝦皮自己的分類標記；
**session 有效卻仍被攔，代表判斷依據是執行環境而非憑證**。

**否決**：改用其他免費雲端（Oracle Always Free 等）。稀缺的不是運算資源，是非機房 IP。

**重新評估**：`.github/workflows/shopee-ci-test.yml` 可手動觸發重驗，不寫入資料庫。

## 3. 瑕疵品標註而不扣分、不隱藏

**日期**：2026-08-27　**狀態**：已實作

**背景**：VFM 獎勵低價，而壞掉的機器正因為壞掉才便宜，因此瑕疵品必然浮到榜首。
實測分數最高的兩筆分別是「瑕疵機」與「外接機」（螢幕已壞）。

**決定**：偵測並標註，不介入評分，另提供隱藏開關。

**理由**：瑕疵該折價多少沒有客觀答案，任何懲罰係數都是憑空訂的，會污染整個評分基準。
而便宜的瑕疵機對能自行維修或拆件的人仍是合理選擇——提供資訊、由人判斷。

**附帶原則**：只標**功能性**瑕疵。外觀使用痕跡是二手常態，全部標註會讓讀者學會忽略徽章。

## 4. 下架判定採時間老化，不採「本次未見」

**日期**：2026-08-26　**狀態**：已實作

**背景**：一次執行將 46 筆蝦皮物件標記為下架。

**決定**：`sweep_stale(source, max_age_days)`，預設 14 天未再出現才標記。

**理由**：本專案所有爬蟲取得的都是**取樣視窗**而非完整庫存（PTT 讀近期文章、

舊集合並非售出，只是被擠出最新清單。

## 5. 行情價差顯示 —— 延後

**日期**：2026-08-27　**狀態**：**延後，條件見下**

**背景**：VFM 分數（如 694.1）單位不明、有假精確，讀者難以判斷「這樣算好嗎」。
曾考慮改為百分位顯示，但百分位是序數，篩選後樣本少時等同排名，資訊量不足。

**決定**：暫不實作，維持現行分數呈現。

**理由**：提案為「推估行情價 = 調整後效能分 ÷ 中位 VFM × 1000」，以金額表達價差。
但實測顯示**模型對不同世代並非中性**：

| 世代 | 筆數 | 組內中位 VFM | vs 全體 |
|---|---|---|---|
| M4 | 24 | 480 | +17% |
| M1 | 31 | 434 | +6% |
| M3 | 25 | 413 | +1% |
| M2 | 36 | 361 | −12% |
| **M5** | **9** | **315** | **−23%** |

若以全體中位數為基準，**每台 M5 都會被說成貴 23%**——那不是洞察，是系統性誤導。
改用同世代中位數可消除偏差，但 M5 僅 9 筆，樣本不足。

進一步以資料反推折舊率：目前的 `每年 ×0.9` 使世代最大偏差 23%，
改為 `×0.95` 可降至 19%，但**剩餘偏差不是折舊率能解決的**——
新機存在「新機溢價」，市場願意為當代機種付超額價格，這是真實市場結構而非模型缺陷。

**重新評估條件**：**每個晶片世代累積 30 筆以上**時重新評估。
屆時同世代中位數才有統計意義，並應同時顯示樣本數，不隱藏不確定性。

## 6. Gemini 維持 3.5 Flash Lite

**日期**：2026-08-27　**狀態**：已確認

**決定**：不更換模型，改為主動節流。

**理由**：配額顯示 RPM 22/15（超標）但每日僅 118/500（充裕）——瓶頸是速率不是額度。
根因是 pipeline 以固定 `sleep(1)` 節流，等同 60 RPM。

**否決**：
- 換 Gemini 3.x Flash（非 Lite）：每日僅 20 次，不敷使用。
- 換 Gemma 4 26B：每日 14,400 次，但實測 4 筆有 1 筆抓不出 `M1 Pro Max` 這類複合晶片名稱，
  而無晶片的物件會被過濾器整筆丟棄。**以解析品質換一個用不到的額度並不划算。**

**重新評估**：每日用量逼近 500，或需一次性大批回填時。
屆時可考慮兩段式：Gemma 先跑、`chip` 為空者再交給 Gemini 複驗。

## 7. 前後端 VFM 公式不一致

**日期**：2026-08-27　**狀態**：**已修正**

**背景**：同一筆物件在 Dashboard 與後端的分數不同，125 筆中有 59 筆（47%）對不上，
最大差距 55 分。

**原因**：形態加權的判定依據不同——後端 `score_engine` 只看 `series` 字串，
前端 `dashboard` 同時看 `series` 與螢幕尺寸。

**影響**：Discord 警報門檻以**後端**分數判定，使用者看到的是**前端**分數。
實測有 7 筆跨在門檻兩側：顯示為「優秀」卻永不推播，或會推播卻顯示為「普通」。

**決定**：採用前端較細緻的分法（區分 Air 13/15、Pro 13/14/16），並**收斂為單一實作**。
`score_engine` 成為唯一的計算入口：持有 `MacBookSpec` 的呼叫端用 `get_vfm_score`，
持有原始 row 的用 `vfm_from_mapping`，兩者共用 `adjusted_score()`。

一併移除三處會再度漂移的重複定義：Dashboard 自帶的基準表與公式、
`mac_spec` 中無人使用卻與 `ScoringWeights` 數值衝突的權重屬性
（`ram_weight` 1.2 vs 1.25、`ModelSeries.weight` Pro13 1.05 vs 1.0）、
以及三處硬編碼的滑桿預設值——現由 `ScoringWeights` 推導。

FastAPI 的權重 query 參數同步改名為 `form_air13` 等五項。

**驗證**：125 筆全數比對，前後端差異 **0 筆**（修正前 59 筆），
跨越警報門檻的分歧 **0 筆**（修正前 7 筆）。並以瀏覽器實測確認網頁顯示的前五名分數
與後端計算完全相同。

## 8. 公開前的資料衛生稽核

**日期**：2026-08-29　**狀態**：已完成

**背景**：專案要從 private 轉公開。公開後任何提交都無法真正收回，因此在轉換前
做一次完整稽核，範圍涵蓋工作目錄與**全部 git 歷史**——後者才是重點，因為
`.gitignore` 只擋未來，擋不住已經進去的東西。

**發現**：現行程式碼乾淨（憑證一律走環境變數，`.env.example` 全為佔位符）。
問題全部在歷史裡，分三類：早期一次 commit 誤帶了 Playwright 的瀏覽器設定檔與
登入 session；提交身分沿用了個人信箱；除錯用的頁面快照裡夾帶第三方個資。

**決定**：以 `git filter-repo` 清除相關路徑並統一提交身分，改用新建的公開 repo
承接乾淨歷史，原 repo 改名保留為 private 封存。

**理由**：force-push 之後 GitHub 仍可能保留無主 commit，且 repo 的 Activity
頁面會留下改寫前的 SHA。**開新 repo 沒有這個問題**——它從來沒有裝過那些物件。
代價只是重設 secrets 與重新部署 Streamlit，換到的是確定性。

**衍生措施**：`CLAUDE.md` 將個資檢查列為強制項目，並明確涵蓋爬蟲抓到的
第三方資料。`.claude/` 這類本機工具設定移出版本控制。

**教訓**：`.gitignore` 是在檔案第一次進 repo **之前**才有用的。一次不小心的
`git add .`，代價是整段歷史。

## 9. 規格抽取寧可缺值，不可猜測

**日期**：2026-08-27　**狀態**：已實作（原則）

**背景**：蝦皮改用精簡模式後失去商品描述，RAM／SSD 的抽取覆蓋率由約 80% 掉到 40%。
追查時發現 regex 不只是抓不到，而是**抓錯**：

```
『澄橘』Macbook Pro 13 2022 M2 8C10G/8G/256G
                        ↑ 8核CPU / 10核GPU
被讀成 RAM=10、SSD=8TB
```

8TB 通過「SSD ≥ 1TB」的門檻取得加成，VFM 因此被推高。

**決定**：所有規格抽取在無法確定時回傳 `None`，並以 Apple 實際出貨的規格清單驗證結果。
同理，晶片抽取遇到賣家堆關鍵字寫出的不存在型號（如「M1 Pro Max」）時取**較低**的一階。

**理由**：缺值有後備機制——由 LLM 補、或由計分器套用預設值，且缺值在 UI 上看得出來。
**錯值沒有任何機制能攔截**，它會直接進入 VFM 公式並產生看似可信的分數。
低估只是少一次機會，高估會發出假的撿漏警報。

**衍生**：`src/scripts/repair_specs.py` 可掃描並修正既有的不可能值。
修復時若任一欄位不合法，則**整組重新抽取**——兩個值來自同一次解析，
倖存的那一半不會因為「剛好是合法規格」就值得信任。

## 10. 測試不得依賴外部服務

**日期**：2026-08-28　**狀態**：已實作

**背景**：專案 4,161 行、**零測試**。過去發現的每個 bug——GPU 核心數被讀成記憶體、
M5 整個世代被丟棄、前後端分數不一致——都是臨時寫腳本手動查出來的，腳本用完即丟，
同樣的錯再犯一次不會有任何機制攔截。

**決定**：建立 pytest 套件，並訂下硬性約束：**沒有 API 金鑰、沒有資料庫也必須全數通過**。

**理由**：這個約束不只是為了讓 CI 跑得動，它會**逼著純邏輯與 I/O 分離**。
實作時立刻付出代價也立刻看到效果：`llm_parser` 原本在模組載入時就建立 Gemini client，
導致連 `extract_specs_from_text`（純 regex，從不呼叫 API）都無法在無金鑰環境下匯入。
改為延遲建立後，該模組才變得可測。

**測試內容取自實際踩過的坑**，不是憑空設計的案例：
`8C10G/8G/256G`、`外觀無傷無碰撞`、`M1 Pro Max`、`鋁合金類macbook`、標題為 `888` 的佔位商品。

**成效**：撰寫過程中即發現一個未知問題——`ShopeeScraper._listing_from_search_item()`
未自行檢查 L1 價格範圍，僅依賴呼叫端過濾，與 Carousell 的對應實作不一致。
已改為方法自身強制，並將上下界抽為具名常數。

**尚未涵蓋**：需要網路或瀏覽器的部分（爬蟲的實際抓取、LLM 呼叫、Streamlit 畫面）。
畫面測試見階段 5 規劃。

## 11. Linter 規則寧可少而準

**日期**：2026-08-28　**狀態**：已實作

**背景**：導入 ruff 時，預設規則在 4,161 行的專案上回報 **145 個問題**。

**決定**：只啟用能抓出 bug 的規則（`F`、`E`、`W`、`I`、`B`、`PLE`、`DTZ`、`RUF`），
關閉純風格項目，並在 `ruff.toml` 中逐條寫明關閉理由。

**理由**：**噪音多到會讓人略過真正的發現，比不裝 linter 更糟。**
關掉的都有具體理由——例如 `BLE001`（捕捉泛用例外）在爬蟲裡是刻意的設計：
單一筆壞資料不得中斷整批；`E701` 針對的 `infer_correct_year` 是寫成 if 鏈的查表，
攤成三倍行數並不會更清楚。

**成效**：導入當下就抓到兩個真問題。

`PLE2510` 指出 `text_extractor.py` 的售價 regex 裡有一個**實體倒退字元**（0x08），
佔據了原本應為 `\b` 的位置：

```
r"([0-9][0-9,]*)([kK])<0x08>"
```

該樣式要求輸入中含倒退字元，永遠不可能匹配——**PTT 上所有寫成「25k」「32k」的售價
一律抽不到**，而那是 PTT 賣家最常見的標價方式。這個字元在編輯器裡不可見，
人工審閱不可能發現。

修正後另加一項測試，掃描全部原始碼中的控制字元，避免同類問題再次潛入。

第二個是 `F821`：修正時區問題的過程中，我在 dashboard 引用了未匯入的 `current_year`，
linter 在執行前就攔下了這個 NameError。

## 12. 文件與程式碼的一致性交給 CI 檢查

**日期**：2026-08-28　**狀態**：已實作

**背景**：測試擋得住壞掉的程式碼，擋不住過期的文件。文件錯了不會有任何一項變紅，
下一個人（包含幾個月後的我）會照著三次 commit 前就不再成立的說明去做。

**決定**：寫 `scripts/check_docs.py`，只驗**機械上可驗證**的宣稱，並同時掛在
pytest 與 CI：

1. 程式讀的每個 env 變數都在 `.env.example`，且 `.env.example` 裡的每個鍵都真的有人讀
2. Markdown 的相對連結都指得到檔案
3. CLAUDE.md 表格標為「✅ 已撰寫」的 spec 確實存在（標 ⬜ 卻存在也算不一致）
4. `score-engine/spec.md` 引用的評分常數與 `score_engine.py` 相符

**理由**：第 4 項是主要動機。**讀者是照那張參數表判斷分數合不合理的**，而那些權重
已經調整過一次；表和程式一旦分岔，整份 spec 就不再能當作判斷依據。

不驗散文，也不驗「文件寫得對不對」——那不可能自動化。只驗數字與路徑，
誤報接近零，開發者才不會學會忽略它。

**導入當下抓到的**：

- `.env.example` 的 `API_HOST` / `API_PORT` 標著「P3 後啟用」，但 API 早已實作，
  而且從不讀這兩個值（`docs/operations.md` 用的是 `uvicorn --port 8000`）。
  看起來可設定、實際上動了沒有任何效果，比缺漏更誤導。
- `score-engine/spec.md` 仍寫著「M5 系列目前為外推值」，實際已換成 Geekbench 6 實測。
- 同一份 spec 要求「新增世代必須同時更新 `benchmark_db.py` 與 `dashboard.py` 的
  `_BENCH`」——那兩處在合併 VFM 實作時就已經是同一個 dict 了。照著做的人會去找
  一個不存在的第二張表。

**自我驗證**：另有一項測試餵給檢查器一份被竄改的 spec，確認它會失敗。
不會失敗的檢查器只是裝飾。

## 13. 瑕疵判定移到 pipeline，結果隨規格一起存

**日期**：2026-08-28　**狀態**：已實作

**背景**：`find_defects()` 的簽名是 `(*parts)`，設計上就要吃標題、`condition` 與內文。
Dashboard 呼叫時確實傳了 `row.get("body_content")`，Discord 那側則根本沒傳。

但 `get_filtered_deals()` 與 `get_all_parsed_deals()` **都不回傳 `body_content`**——
它們把 `parsed_json` 展開，再外加 `original_title` / `url` / `status` / `source`。
所以 Dashboard 傳進去的永遠是 `None`。

結果：**只寫在內文的功能性故障，對整個系統不存在**。而 PTT 賣家正是把機況寫在內文，
標題只放型號與售價。

**決定**：判定移到 `src/main.py` 存檔前執行——那是全系統唯一還握著 `body` 的位置——
結果存進 `parsed_json` 的 `defects` 欄位。下游一律經 `defects_for(row)` 取用，
沒有該欄位的舊資料退回只看標題與 `condition`。

**否決的方案**：讓 `get_filtered_deals()` 一併回傳 `body_content`。
改一行就好，但 Dashboard 每次重繪都會把所有內文從 Neon 拉一次（每動一次滑桿就重跑），
而它只需要那幾個字串裡的一個布林結論。算一次、存起來，前後端也就不可能再各算各的。

**先前的判斷是錯的**：我一開始說這是前後端不一致。不是。
`main.py` 當時傳的是 `(original_title, condition)`，Dashboard 傳的是
`(title, condition, body_content=None)`——**兩邊算出來的結果一致，而且一致地錯**。
Discord 與網站互相印證，只是都看不到內文。

## 14. 瀏覽器測試：只驗會默默壞掉的東西

**日期**：2026-08-28　**狀態**：已實作

**背景**：其餘所有測試都在測函式。分數算對了、卻 render 進一個在手機上撐破畫面的
元素，對使用者而言一樣是失敗，而專案裡沒有任何東西會發現。最初的需求就是
「手機端網頁幾乎沒可讀性」。

**決定**：`tests/e2e/` 自建一個固定的 SQLite 測試資料庫（9 筆寫死的物件），
用真正的進入點 `streamlit_app.py` 把服務跑起來，再用 Playwright 驗四件事：

1. 卡片上的分數等於 `score_engine` 算出來的分數
2. 瑕疵徽章出現在標題／`condition`／內文三種來源，且乾淨物件不誤標
3. 320／390／1440px 都不橫向捲動，卡片內文不溢出卡片
4. 零 JS 錯誤、無 traceback 洩漏進頁面

**刻意不驗**設計好不好看——那不可能自動化，也不該由 CI 決定。

**測資是寫死的**，所以每個斷言都有已知的正確答案；分數是拿 `vfm_from_mapping`
現算來比對，不是把畫面上的數字抄下來當期望值——那種測試永遠會通過。

**兩個踩到的坑（都在我自己的測試程式裡）**：

- `subprocess.PIPE` 接了 Streamlit 的 stdout 卻從不讀。**OS pipe 緩衝區滿了以後
  Streamlit 會卡在寫入而停止服務**：前幾次載入正常，之後每一次都 60 秒逾時。
  首次執行 1 失敗 11 錯誤、耗時 11 分 51 秒。改成導向檔案。
- `page` fixture 是 function-scoped，13 個測試各自重載頁面。改成 session-scoped
  共用一個頁面，只有會點擊 widget 的測試另開 context，並用 fixture 在結束時
  把 viewport 復原。**20.18 秒，19 項全過。**

## 15. 支援 MacBook Neo（A18 Pro）—— 寫死家族的老問題換個形狀再犯

**日期**：2026-08-28　**狀態**：已實作

**背景**：旋轉拍賣抓到一筆「MacBook Neo 8G/256GB」，售價 20,700。
我一開始判斷它是借用名稱的山寨機。**錯了**——MacBook Neo 是 Apple 2026 年 3 月推出的
$599 機種，也是第一台採用 iPhone 晶片（A18 Pro）的 Mac。

**問題**：`_CHIP_RE` 只比對 `\bM(\d{1,2})...`，A18 Pro 抽不到晶片，
而 `_INVALID_CHIPS` 會把無晶片的物件整筆丟棄。**這台機器對系統不存在。**

這正是本檔 #3（M5 被靜默丟失 9 筆）同一個成因換了形狀：當時是寫死世代清單停在 M4，
這次是寫死家族前綴只認 M。**「不得寫死清單」那條規則的範圍原來比我當初寫的更大。**

**決定**：

- 基準分 `A18 Pro: 8668`（Geekbench 6 多核，與全表同一來源），略高於 M1 的 8,500，
  與發表時的評測結論一致。
- 抽取改為 `\b([MA])(\d{1,2})\s*(PRO|MAX|ULTRA)?\b`。
- **A 系列排序一律低於任何 M 系列**，否則 `A18` 會在數字上壓過 `M5`。
- **裸寫的 `A18` 正規化為 `A18 Pro`**。Apple 只出過這一顆 A 系列 Mac 晶片；
  不正規化會落到 5000 預設分，等於賣家少打兩個字分數就砍半——
  與 #4 那個年份推論 bug（同機種 432 vs 204）同一類的失真。
- 形態歸入 `air13`（13 吋無風扇入門機），否則會落進 `pro13` 這個預設分支。

**碰撞檢查**：Apple 機身型號是 `A` + 4 位數（`A2338`、`A1706`），
`\d{1,2}` 後面接不到 `\b`，不會誤判。已寫成測試。

**教訓**：我把一台沒見過的機型判斷成山寨，是**用「我沒聽過」代替查證**。
硬體會出新型號，而這個專案的價值完全建立在能不能認得它們。

## 16. `last_seen` 只能由「真的看到」來更新

**日期**：2026-08-28　**狀態**：已實作

**背景**：查一件無關的事時發現，一次 `--source shopee` 的本機排程，把 PTT 與旋轉拍賣的
資料也改寫了——三個來源的 `last_seen` 都落在同一分鐘。

追下去是 Step 2 解析迴圈：它 `db.get_all_deals()` 掃**全表**、不管 `--source`，
然後用 `db.save_deal()` 寫回結果。而 `save_deal()` 會更新 `last_seen`。

**為什麼嚴重**：`sweep_stale()` 的整個前提是「`last_seen` = 我們最後一次在平台上
看到這筆」。解析迴圈**從不重新抓頁面**，它只讀資料庫裡已存的標題與內文——卻宣稱看到了。

於是任何解析不完整的資料每晚都被蓋成「剛看到」，**永遠不會過期**。
實測 **186 筆中有 121 筆**處於這個狀態。最糟的是那些「缺的欄位本來就不在存下來的文字裡」
的資料：永遠解析不完整 → 永遠需要修復 → 永遠被刷新 → 永遠以「在售中」留在網站上。

**決定**：拆成兩個方法。`save_deal()` 記錄一次目擊、更新 `last_seen`；
新的 `update_parsed()` 只改 `parsed_json`。規則寫進 `database/spec.md`：
**沒有真的去平台上看過，就不准動 `last_seen`。**

## 17. 修復條件不得由修復動作自己滿足

**日期**：2026-08-28　**狀態**：已實作

**背景**：解析迴圈的 `needs_fix` 條件之一是 `p_json.get("location") == "未知"`。
而同一個迴圈的結尾是：

```python
if not res_dict.get("location") or res_dict.get("location") == "未知":
    res_dict["location"] = "未知"
```

**修復動作產生了讓它需要修復的那個值。** 這 69 筆資料每晚各花一次 Gemini 呼叫，
永遠不會成功，佔當時每晚 LLM 呼叫的 **57%**。

**決定**：移除該條件。`location` 是卡片上的一個顯示欄位，值不值得為它打一次 LLM
是另一回事，但**用一個保證不會成立的條件去觸發它，只會是純粹的浪費**。

**通則**：任何「需要處理」的判定，都要確認處理動作真的會讓它變成「不需要處理」。
不然就是寫了一個每晚執行的無限迴圈，而且不會有任何東西報錯。

## 18. 解析成本必須與新物件數量掛鉤，不是與資料庫總量

**日期**：2026-08-28　**狀態**：已實作

**背景**：`MAX_LLM_CALLS_PER_RUN` 只在蝦皮爬蟲內生效，**解析迴圈完全沒有上限**。
而它掃全表，所以成本隨資料庫**總量**成長：

| 資料庫規模 | 每晚 LLM 呼叫 |
|---|---|
| 186 筆（當時） | 121 |
| 500 筆 | 約 325 |
| **約 770 筆** | **500 —— 撞上 Gemini 免費方案每日上限** |

到那時整條 pipeline 每晚失敗，而症狀會像「Gemini 壞了」，很難追到真正的原因。
**這種 bug 在資料量小的時候完全看不出來，等看得出來的時候已經在生產環境爛掉了。**

**決定**：

1. **解析指紋**。把這次解析所讀的 `title + body` 的雜湊存進 `parsed_json`。
   下次執行時若雜湊沒變，代表要問的是**同一個問題**，跳過。
   物件被重新抓取而文字改變時，雜湊跟著變，自動恢復重試。
2. **`MAX_REPAIR_CALLS_PER_RUN`（預設 50）** 作為兜底上限。
3. 解析迴圈只處理**這次有跑的來源**（`--skip-scrape` 除外，那個模式的用途就是重解析全部）。

**成效**：每晚 121 次 → 第一晚 50 次 → 之後 0 次（除非有新物件或文字有變動）。

**否決的方案**：單純加上限、每晚輪流修一批。實作簡單，但那只是把浪費攤平到更多天，
沒有解決「同樣的問題問一輩子」這件事。

## 19. 可執行的腳本，不是要人照著重打的註解

**日期**：2026-08-28　**狀態**：已實作

**背景**：本機排程的註冊指令寫在 `run_local_shopee.ps1` 的檔頭註解裡，
`docs/setup.md` 則寫「依檔頭註解註冊工作排程器」。也就是說換電腦的程序是
**讀一段註解、手動重打一次**。

檢查時發現註解和實際註冊的內容**已經不一樣了**——註解寫 `push to Neon`，
實際是 `push results to Neon`。差一個字沒有影響，但它證明了這種做法必然漂移，
而且漂移不會有任何東西報錯。真正的代價是：換電腦時照著註解打，會得到一個舊版本的設定

**決定**：改成 `scripts/install_schedule.ps1`——**這個檔案就是排程的定義**，不是描述。
要改時間或來源就改參數重跑，它會就地覆寫。同時在註冊前檢查 venv、`.env`、

`docs/setup.md` 補上「換電腦」章節，明確列出**四樣不在 repo 裡的東西**
（venv、`.env`、`shopee_state.json`、Windows 工作排程）以及各自為什麼不在。
資料本身不用搬——它在 Neon。

**通則**：任何需要人照著重打才能重現的程序，都應該視為尚未寫下來。

## 20. 旋轉拍賣移到本機執行

**日期**：2026-08-28　**狀態**：已實作

**背景**：`carousell.py` 的模組註解原本宣稱：純 HTTP、伺服器端渲染、不需瀏覽器，
所以「可在 GitHub runner 上原樣執行，不像蝦皮」。2026-08-28 的排程以
`403 Forbidden` 失敗，證明那句話是錯的。

**量測**（`src/scripts/probe_carousell.py`，手動觸發的 workflow）：

| | GitHub runner | 住宅 IP |
|---|---|---|
| 5 種標頭（含現行、最新 Chrome、完整瀏覽器標頭、誠實爬蟲 UA、無標頭） | **5/5 403** | 5/5 200 |
| 5 個路徑（sitemap、sitemap 索引、robots.txt、首頁、商品頁） | **4/5 403** | 5/5 200 |

唯一通過的是 `robots.txt`。**這是 CDN bot 管理的典型特徵**——刻意放行 robots.txt
讓爬蟲讀得到規則，其餘一律擋。所以是針對資料中心 IP 的政策，不是路徑問題，
也不是渲染方式的問題。三次獨立的 runner 執行結果一致。

**決定**：CI 只跑 PTT；旋轉拍賣與蝦皮一起在本機排程執行，旋轉排在前面
（純 HTTP、約一分鐘，先跑完就不受蝦皮瀏覽器路徑卡住的影響——排程上限是一小時）。

**為什麼不留在 CI 讓它失敗就好**：那會每晚發一則「旋轉拍賣：爬取失敗」，
而那是一個**永遠不會自己好的已知狀況**。天天喊狼來了，真的失敗時也會被一起忽略——
與瑕疵徽章、linter 規則篩選是同一個原則。

**沒有測到的部分**（誠實記下）：付費住宅代理沒測，但它一定可行，這個量約 $2/月。
Carousell 的 `api-service` 端點、其他網域、IPv6 都沒測。所以精確的說法是
**「在不花錢的前提下只能本機」**，不是「技術上做不到」。

**保留量測工具**：WAF 規則會變。probe 腳本與 workflow 都留著，
日後想確認封鎖是否解除，執行一次就有答案，不必重新推理。

## 21. 429 是兩種問題共用一個狀態碼

**日期**：2026-08-28　**狀態**：已實作

**背景**：套用完本機排程後手動觸發一次，Gemini 開始回 429。`llm_parser.py` 的重試
邏輯註解直接寫著「A 429 here is the per-minute quota」，於是每次都睡 65 秒再試。

但那次的 429 是**每日**額度：

```
quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier
limit: 500
```

**RPD 要等到太平洋時間午夜才重置，睡 65 秒毫無意義。** 實測結果：那次執行 20 分鐘裡
出現 24 次 429、睡掉 18 分鐘，只處理到第 19 筆（共 160 筆），照這個速度會在排程的
一小時上限被砍掉——**Step 3 到 7（評分、警報、下架判定、heartbeat）一個都跑不到**。

**決定**：判讀錯誤內的 `quotaId` 而非訊息文字（文字會改版，quotaId 不會）。
每分鐘額度維持原本的等待重試；每日額度拋出 `GeminiDailyQuotaExhausted`，
解析階段立刻中止，pipeline 帶著已解析的資料繼續走完剩下的步驟。

**額度為什麼今天就用完**：今早 09:41 那次排程跑的是**修正前的舊程式碼**——
無上限地重新解析全表 121 筆。加上蝦皮爬蟲本身的 LLM 呼叫（**共用同一個 500 次額度**，
這點我在 #18 的估算裡漏掉了），所以我當時估的「約 770 筆才會撞牆」太樂觀，
實際上當天就撞到了。

**Discord 的呈現**：額度用盡**不算爬取失敗**。所有來源都可能抓得好好的，只是沒解析完；
報成「爬取失敗」會讓人去查爬蟲，查錯方向。改成獨立一行的 🪫 提示，
而來源真的失敗時仍然優先顯示 ⚠️。

**順帶補上 #18 的漏洞**：被晶片過濾丟棄的物件先前不會記錄解析指紋，
所以每次執行都會重新問一次同樣的問題——正是這個預算機制要防的事。
現在會記錄，但**只針對已經有 parsed_json 的資料**：替從未解析成功的資料寫入一個
只含指紋的 parsed_json，會讓它出現在 Step 3 的評分輸入裡（該處只檢查 parsed_json 非空）。
從未解析成功的資料，一天重試一次是合理的。

## 22. 列表改版：結果列，機型當大字

**日期**：2026-08-28　**狀態**：已實作

**背景**：最初的三個問題裡，UI 是唯一沒動過的——「表格固定格式、有點醜，手機端幾乎沒可讀性」。
先做完邏輯與測試才動它，是因為**改 UI 需要安全網**：現在有 e2e 測試守著
320／390／1440px 不橫向溢出、卡片分數與後端一致、零 JS 錯誤，所以可以放手改。

**決定與理由**：

- **卡片改為髮絲線分隔的資料列。** 舊版每個欄位權重都一樣，眼睛不知道先看哪個。
  航班與比價網站的做法是讓價格對齊成一欄，眼睛直接往下掃。
- **機型當大字，賣家原標題退為灰色副標。** 賣場標題把型號埋在店名、優惠標語與貨號裡
  （`『澄橘』Macbook Air 15 2025 M4 10C10G/16G/256G 午夜 瑕疵機《二手》A87078`）。
  這不只是排版——**系統開始為自己的解析結果背書**，顯示的是結論而不是原文。
  原標題保留，因為它是唯一能核對上面那行的依據。
- **分數單位標在清單上方一次，不是每列。** 「CP」沒有回答任何事。這個數字有真實單位：
  公式是 `效能分 × 折舊 × 加成 ÷ 售價 × 1000`，所以就是**每千元買到的效能分**，可以驗算。
  標頭同時放中位數——**750 要先知道中間值是 415 才有意義**。
  這與 #6 否決百分位並不衝突：中位數是當下的事實，不是排名宣稱。
- **淺色。** 使用者判斷更接近蘋果調性。
- **Inter + Noto Sans TC，數字用 `tabular-nums`，不用等寬字。**
  等寬字是開發工具的語言。Apple 從不用它排價格，而是用 SF 搭配等寬數字——
  **這是「工具感」與「產品感」的分界，比選哪個字體影響大。**

**被否決的**：

- **留白版（大量空白、細體大字）**：「比較美觀但資訊閱讀不容易」。
  對一個每天回來掃一眼的工具，可讀性優先。
- **首頁 hero 大圖／slogan**：那是比價網站「首頁」的做法，而 mac-valuer 只有結果頁。
  放上去會吃掉手機第一屏——正是最初抱怨的那個問題。
- **SF Pro／PingFang TC**：Apple 的字體授權只允許用於 Apple 平台的 App，
  放在公開網站當 webfont 是違反授權的。Inter 是最接近的免費替代。

**自己犯的同一個錯**：第一版改完，手機上標題與統計列吃掉整個第一屏，
**第一筆物件在摺線以下**——就是我拿來否決 hero 的那個理由。
已修（標題限高、統計改兩欄、價格區間排到最後）。

## 23. 規則改變時，已存的資料不會自己跟上

**日期**：2026-08-28　**狀態**：已實作

**背景**：修好 Intel Core m5 被誤判為 Apple M5 之後，**那台 2016 年的機器仍然掛在網站榜首**，
分數 1060。修正只作用於新的解析；資料庫裡既有的 `chip=M5` 不會因為規則變了就自動重算，
而它的 `parsed_json` 是完整的，解析迴圈也不會回頭碰它。

**決定**：寫 `src/scripts/revalidate_chips.py`，以**現行規則**重新檢驗每一筆已存的晶片。
不通過的清掉 `parsed_json` 而非刪除整列——物件確實存在，只是超出範圍，
而「沒有解析結果」本來就是 pipeline 表示這件事的方式（所有讀取路徑都要求 `parsed_json` 非空）。

**通則**：**判定規則改變時，要問「已經存下來的資料怎麼辦」。**
只修程式碼會留下一批依舊照舊規則產生的資料，而且它們通常正是當初讓你發現問題的那幾筆。

  air13／pro14／pro16，而 Mac mini 沒有螢幕。真要收非筆電機種，

## 27. 一個 bug 的兩層：壞掉的，和慢到像壞掉的

**日期**：2026-08-28　**狀態**：已實作

**回報**：「按下一頁，看到 loading 模糊畫面，但還是停留在原本頁面。」

查下去是兩個獨立的問題疊在一起，而**先找到的那個不是主要成因**。

### 一、下一頁真的沒有作用

頁碼下拉選單同時給了 `key="pg_select"` 和 `index=current_page - 1`。
**Streamlit 的 widget 一旦有 key，session_state 裡存的值會蓋過 `index`。** 於是：

```
按下一頁 → page_num = 2 → rerun
下拉選單還原成存著的 1（index 被忽略）
1 != 2 → 把 page_num 設回 1 → 再 rerun
```

**按鈕的動作被旁邊的元件抵銷了**，而且跑兩次 rerun——所以會看到兩次模糊。

修法：讓下拉選單自己擁有那個狀態（`key="page_num"`），按鈕改用 `on_click` 回呼
在 rerun 前寫入。單一來源，沒有第二個元件能覆寫它。

### 二、每次互動 4.5 秒

實測每次 rerun 對 Neon 查四次，每趟約 1 秒：

| 查詢 | 耗時 |
|---|---|
| `get_filtered_deals`（篩選後） | 1.58s |
| `get_filtered_deals`（未篩選基準） | 0.91s |
| `get_new_count` | 1.00s |
| `get_last_seen` | 1.02s |

**翻頁不改變任何篩選條件，卻付了全額。** 加上 `@st.cache_data(ttl=300)` 後
**5.0 秒 → 0.3 秒**。資料一天只在排程時變一次，五分鐘的快取遠比那短。

### 教訓

我一開始只看程式碼就斷定是 `key`/`index`，測完卻發現舊版的「上一頁」會改變清單——
證據矛盾。**是加了快取、把延遲拿掉之後，功能性 bug 才乾淨地顯露出來**
（舊控制項按兩次下一頁後，上一頁仍是 disabled）。

**慢會偽裝成壞。** 在延遲被排除之前，任何互動的行為觀察都不可信。

兩個都加了瀏覽器測試：翻頁必須換一組物件、回上一頁必須回到原本那組、
且反覆翻頁要能走遍全部測資。

## 28. 通報者不能活在被通報的東西裡面

**日期**：2026-08-29　**狀態**：已實作

**背景**：2026-08-29 10:02:46 排程啟動，10:02:51 死亡，全程五秒，**Discord 一個字都沒有**。

事件記錄檔（`Microsoft-Windows-CodeIntegrity/Operational`）：

```
Event 3077 / 3033
process …\Python313\python.exe attempted to load
  …\venv\Lib\site-packages\pandas\_libs\tslibs\timezones.cp313-win_amd64.pyd
did not meet the Enterprise signing level requirements
  (Policy ID:{0283ac0f-fff1-49ae-ada1-8a933130cad6})
```

該 Policy ID 是**智慧型應用程式控制（Smart App Control）**，本機為強制執行
（`VerifiedAndReputablePolicyState = 1`）。它封鎖未簽章且雲端信譽查不到的執行檔，
而 pandas 的 `.pyd` 全部未簽章。

**這不是版本問題**：pandas 3.0.5 於 8/25 安裝，8/26、8/27、8/28 三天都正常執行。
過去十天的全部 Code Integrity 封鎖事件中，**與 python 有關的只有這一次**
（同一秒的 3077 + 3033 兩筆）。事後手動 `import pandas` 亦正常。
結論是**間歇性的信譽查詢失敗**，不是永久封鎖。

而通知之所以完全沒發出，是三層都沒接住：

| 層 | 為什麼沒接住 |
|---|---|
| `src/main.py:9` `import pandas` | 死在這裡。通知器在**第 15 行**才 import，模組連載入都沒有 |
| `send_heartbeat()` | 在 Step 7，`run_valuation_pipeline()` 的最後 |
| `__main__` | 裸呼叫，沒有 try/except |
| `run_local_scrape.ps1` | 把 `exit code 1` 寫進 log 然後結束，**沒有任何人讀那個結束碼** |

**決定**：失敗通知改由 PowerShell 包裝層發出，並加上一次條件式重試。

1. **通知從 python 之外送出**。`Send-FailureNotice` 自行讀 `.env` 取得 webhook，
   附上 log 尾端 12 行。已實測發送成功。
2. **快速失敗才重試**（`$FastFailSeconds = 300`）。300 秒內死亡代表根本沒啟動——
   DLL 被擋、session 檔不見、資料庫連不上——重試幾乎免費；二十分鐘後才死代表已經
   做了很多事，而排程有一小時上限（`install_schedule.ps1`），重試可能被砍在寫入中途。
3. **`__main__` 補 try/except**，涵蓋 pipeline 內部的致命錯誤。
   `_heartbeat_content` 新增 `fatal` 分支：中止的執行**不印「觸發警報：0 筆」**——
   那句話是真的，但讀起來像平靜的一晚。

**理由**：**負責通報的東西不能與被通報的東西同生共死。** 任何由 python 發出的通知，
在 python 起不來時一定不存在。這是 #21（爬蟲壞掉被顯示成「0 筆」）的更高一層：
當時的問題是訊息內容指向錯誤的地方，這次是**根本沒有訊息**。
**沉默沒有形狀——沒有人能對一則從未抵達的訊息設警報。**

**否決**：

- **關掉 Smart App Control**。它是全開或全關，且關閉後需重灌 Windows 才能再啟用；
  而且它擋的確實是未簽章的二進位檔，關掉是拿整台機器的防護換一個排程的穩定性。
- **只在 python 端補 try/except**。這是三層裡最容易做的一層，也是唯一涵蓋不了
  今天這種失敗的一層。單獨做它會製造「已經修好了」的錯覺。

**重新評估**：若 SAC 再擋到其他檔案、或出現重試也救不回的案例，
300 秒的快速失敗門檻要重新檢視。

## 30. CI 的依賴清單不再手寫

**日期**：2026-08-29　**狀態**：已實作

**背景**：`pytest` job 長期在 collection 階段就失敗，一個測試都沒跑到。安裝步驟手列了
八個套件，實際需要十二個——測試 import `src.scrapers`，其 `__init__` 會載入全部三個

「1 failing and 1 successful」——**一半綠的比全紅的更容易被略過。**

**決定**：改為 `pip install pytest ruff -r requirements.txt`。

**理由**：手寫的依賴清單，是一份「已經存在於別處的事實」的副本。本專案已經修過四次

**修正的錯誤前提**：原本不用 requirements.txt 的理由寫在註解裡：「playwright 和
camoufox 會抓瀏覽器二進位檔」。實測 `pip install` 並不會，抓的是 `playwright install`。
證據就在同一個檔案裡：browser job 額外寫了 `python -m playwright install
--with-deps chromium`，若 pip 就會抓，那行不需要存在。

**代價**：實測完整安裝 27 秒。`pytest` job 的設計目的是「兩分鐘內回報邏輯迴歸」，
這個增量在預算內。

**重新評估的條件**：若安裝時間成長到讓 job 超過兩分鐘，再考慮拆一份
`requirements-test.txt`，並用 `check_docs.py` 機械驗證它涵蓋所有 import——
清單可以存在，但不能靠人記得同步。

## 31. 公開改用新 repo，而不是改寫舊 repo 後強推

**日期**：2026-08-29　**狀態**：已完成

**背景**：稽核（#8）發現歷史裡有登入 session 與個資，必須在公開前清除。
手段有二：在原 repo 上 `git filter-repo` 改寫後 force-push，
或把乾淨歷史推到一個新建的 repo。

**決定**：新建 repo 承接乾淨歷史，原 repo 改名為 `mac-valuer-archive` 並維持 private。

**理由**：force-push 之後 GitHub 仍會保留一段時間的無主 commit，理論上可經完整 SHA 存取。
更關鍵的是 **repo 的 Activity 頁面會留下改寫前後的 SHA**，而那頁會隨 repo 一起公開——
等於把鑰匙留在門口。官方對「移除敏感資料」的建議因此包含聯絡 GitHub Support 清除快取，
那是一個沒有明確完成時點、也無法自行驗證的步驟。

新 repo 沒有這個問題：**它從來沒有裝過那些物件**，所以不需要相信任何清除動作有生效，
可以直接驗證。

**否決的方案**：

- **在原 repo force-push**：省下重設 secrets 與重新部署，但把「清乾淨了嗎」
  變成一個要靠 GitHub 內部行為與 Support 回應才能回答的問題。
- **刪除原 repo 再同名重建**：一樣乾淨，但刪除不可逆，而且**同名重建會放棄
  GitHub 90 天內還原刪除 repo 的機制**。改名封存有同樣效果，且隨時能退回。

**代價**：重設 4 個 Actions secret、重新部署 Streamlit、重填 About，實測約 20 分鐘。
原 repo 改名後名稱立即釋出，新 repo 沿用原名，因此程式碼中三處寫死的 repo 網址不必修改。

**驗證**：以不帶任何憑證的 `git clone` 取得公開 repo，掃描全物件庫，個資命中 0。
**驗證必須從外部做**——在本機或已登入的環境檢查，看到的不是訪客看到的東西。

**重新評估的條件**：`mac-valuer-archive` 仍含完整洩漏歷史，只是 private。
它同時是還原點與未爆彈。新 repo 穩定運作後應刪除，不要無限期保留。

## 32. Streamlit app 的公開設定，與 repo 的公開設定是兩回事

**日期**：2026-08-29　**狀態**：已修正

**背景**：repo 轉公開後，`mac-valuer.streamlit.app` 對未登入訪客仍回 303，
重導到 `share.streamlit.io/-/auth/app`。但用無痕視窗測試看起來完全正常。

**原因**：無痕視窗內的分頁**共用 cookie**。修 app 時在同一個無痕視窗開過
`share.streamlit.io`，因此帶著登入 cookie；auth 那一跳靜靜通過又轉回來，
畫面與正常無異。真正的匿名訪客會停在登入頁。

**決定**：Streamlit Community Cloud 的 app 分享設定必須單獨改為 public。
repo 公開不會連帶讓 app 公開。

**驗證方法**：用 `curl` 而不是瀏覽器。但 curl 預設不保存 cookie，
Streamlit 的 session 交握會因此變成無窮重導，看起來像壞掉——**必須帶 cookie jar**：

```bash
curl -s -L -c cj.txt -b cj.txt -o /dev/null      -w '%{http_code}
' https://mac-valuer.streamlit.app
```

`200` 才算通過。這個坑踩了兩次：先用一般瀏覽器誤判成好的，
再用無 cookie 的 curl 誤判成壞的。

**教訓**：驗證「訪客看得到什麼」時，**測試環境本身的狀態就是變數**。
`docs/operations.md` 已記過一次同類實測（用未登入瀏覽器確認訪客看得到哪些元件），
這次是同一個陷阱換了個形狀。
